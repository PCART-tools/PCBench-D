This directory produces the dataset shared by RQ1, RQ2, and RQ3: real **deprecated-API → replacement-API mappings**, each derived from a library's changelog and accompanied by source-definition removal and original-invocation failure version information.


## Data Sources

The data comes from `33` popular Python third-party libraries (taken from PCBench), with the main information drawn from each library's changelog or release notes.

Two cutoff dates are used:

- **Dataset-construction cutoff:** `2025-03-18` — only changelogs released before this date are collected.
- **Lifecycle-observation cutoff:** `2025-08-01` — invocation verification tracks up to this date.


## Collection Process

The overall process has four steps and ends with `final_dataset.xlsx`.

### Pilot Study: Determine the Screening Scope and Keywords

Deprecation information appears both in dedicated sections and scattered elsewhere in changelogs. A small-scale pilot study first identifies the common dedicated deprecation-related section names and deprecation-related retrieval keywords used as the basis for formal collection. See [pilot study/](pilot%20study/).

### Collect Deprecation Entries from Changelogs

Each library's changelogs are manually screened entry by entry:

- all entries in dedicated deprecation-related sections;
- entries matching keywords in other sections.

An entry and its same-release context must explicitly name both the deprecated API and its replacement. Library documentation is used only to confirm API identity, not to infer an unstated replacement.

### Identify Source-Code Facts

For each API pair, the granularity, definition location and content, and source link are collected. The version in which the deprecated API's source definition was removed is also determined:

- **Announcement release:** Record the deprecated API's definition in the last release before the announcement, and the replacement's definition in the announcement release. If the deprecated definition was already removed before the announcement, record it in the release before its removal instead.
- **Removal release:** Record the deprecated API's definition in the release before removal, and the replacement's definition in the removal release.

### Build Invocation Cases and Measure the Failure Version

For each mapping, an original invocation is generated and executed across releases to obtain the original-invocation failure version. The invocation cases are first generated by [invocation case generation/](invocation%20case%20generation/), then manually reviewed, tested, and iteratively adjusted until the invocation targets the intended API. The final test cases are placed under `Benchmark/invocation_cases`.


## Final Dataset

The final result is `final_dataset.xlsx`, containing `830` mappings:

| API Granularity | Count |
| --- | ---: |
| Class | 207 |
| Function | 239 |
| Method | 384 |
| **Total** | **830** |

The file is split into worksheets by library, one worksheet per library. Each row is a mapping, with the following columns:

| Column | Meaning |
| --- | --- |
| `documented_deprecation_version` | Documented deprecation-announcement version |
| `original_deprecation_log` | Original deprecation log entry |
| `deprecated_api_fqn` | Fully qualified name of the deprecated API |
| `replacement_api_fqn` | Fully qualified name of the replacement API |
| `granularity` | API granularity (`class`, `function`, or `method`) |
| `last_version_before_removal` | Last version before source-definition removal |
| `removal_version` | Source-definition removal version |
| `actual_invalid_version` | Original-invocation failure version |
| `deprecated_api_source_link` | Source link of the deprecated API |
| `replacement_api_source_link` | Source link of the replacement API |

The three version columns use the following value conventions:

- `last_version_before_removal`: `still exists in <version>` means the source definition was **not yet removed** as of the lifecycle-observation cutoff (`2025-08-01`), and `<version>` is the latest release at that cutoff; otherwise the cell holds the last version in which the definition still existed.
- `removal_version`: an empty cell means **not yet removed**; it is left blank because the adjacent `last_version_before_removal` already records the `still exists in <version>` status, so the fact is not repeated.
- `actual_invalid_version`: `end` means the invocation had **not yet failed** by the cutoff (`2025-08-01`); otherwise the cell holds the version at which the invocation first fails.
