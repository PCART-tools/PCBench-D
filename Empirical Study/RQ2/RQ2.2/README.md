RQ2.2 analyzes key versions in the API migration process. The study considers two migration scenarios, `fix_D` and `fix_R`, and focuses on the following three questions:

1. How the identified key versions are distributed across different migration phases;
2. The dominant causes of key-version occurrences and their attribution results;
3. How candidate-related factors affect key versions.

The scripts in this directory perform statistical analyses on already-generated similarity-ranking results and key-version cases. They do not recompute API similarity.

The ranking files use the implementation identifiers `mapBased`, `tokenBased`, and `treeBased` for the paper's **graph-based**, **token-based**, and **tree-based** algorithms. The cause-directory names `dep_rep`, `common_cause`, and `candidates_cause` correspond to the paper's **pair-dominant**, **mixed**, and **other-candidate-dominant** categories.

---

## 1. Input Data

RQ2.2 uses three types of data: Excel inputs, case data, and the cause-based reorganization of cases in `cases_split`.

### 1.1 Excel Input

The `input/` directory contains two Excel files:

```text
input/
├── fix_D.xlsx
└── fix_R.xlsx
```

The two files correspond to the `fix_D` and `fix_R` migration scenarios, respectively. Each file contains worksheets for different API granularities and migration-related cases, such as:

```text
class_transition
function_transition
method_transition
```

Column K in the Excel files is `Key_Versions`. This column stores the key-version information identified during the preceding similarity-ranking analysis. A total of **306 key versions** were identified. The key versions are stored in each cell as a comma-separated list of version numbers.

The Excel files also contain API names, API granularities, version boundaries, and similarity results. The specific fields used depend on the implementation of each script.

### 1.2 `cases` Data

After the key versions are identified, the similarity-ranking information corresponding to these 306 key versions is extracted from the result directory generated by `measure_similarity` and organized into cases under `cases/`.

A typical structure is:

```text
cases/
├── fix_D/
│   ├── consistent/
│   │   ├── class/<case>/
│   │   ├── function/<case>/
│   │   └── method/<case>/
│   └── no_consistent/
└── fix_R/
    ├── consistent/
    ├── no_consistent/
    └── ...
```

The `consistent` / `no_consistent` split records whether the applicable similarity methods agree on the ranking trend for the case (the paper's *method agreement* / *method disagreement*).

Each case represents one API migration instance and generally contains candidate-API ranking results for two adjacent version stages:

```text
<case>/
├── result/
│   ├── Vi-1_*/
│   │   ├── mapBased.json
│   │   ├── tokenBased.json
│   │   └── treeBased.json
│   └── Vi_*/
│       ├── mapBased.json
│       ├── tokenBased.json
│       └── treeBased.json
└── analysis.md (used by some historical analysis workflows)
```

Here:

- `Vi-1` is the release immediately before a key version and `Vi` is the key version itself (the paper's `v_i` and `v_{i+1}`); the `Vi` prefix is a generic release index, unrelated to the original-invocation failure version `Vi` used in RQ3.
- Algorithm JSON files generally contain `api_name`, `score`, and `rank`.

### 1.3 `cases_split` Data

After the dominant-cause analysis, the cases are reorganized according to their cause classifications into `cases_split/`:

```text
cases_split/
├── candidates_cause/
│   ├── fix_D/
│   └── fix_R/
├── common_cause/
│   ├── fix_D/
│   └── fix_R/
└── dep_rep/
    ├── fix_D/
    └── fix_R/
```

The three cause directories correspond to the paper's dominant-cause categories:

- `candidates_cause` (the paper's *other-candidate-dominant*): changes in other candidates, including their presence or code, dominate the attribution;
- `common_cause` (the paper's *mixed*): the attribution is mixed because of equal candidate-level effects, a method-level tie, or disagreement across methods; it does not necessarily imply equal contributions from both sources in the same method;
- `dep_rep` (the paper's *pair-dominant*): changes in deprecated/replacement API similarity dominate the attribution.

Within each cause directory, cases are further organized by `fix_D` / `fix_R`, consistency category, and API granularity. On Windows, a case may be represented by a text file containing a relative-path reference; the analysis scripts resolve these references to the actual directories under `cases/`.

# 0.mark_rank_transitions.py

This script identifies adjacent version transitions with large rank changes and writes the corresponding transition markers to column K (`Key_Versions`) of an Excel workbook.

## 1. Overview

For each worksheet, the script:

- reads the version-ranking JSON from column H;
- examines adjacent version pairs in the JSON `order` list;
- checks whether any method's rank changes by at least 10% of the previous version's total, subject to a minimum previous total;
- records each qualifying transition in column K.

The input workbook is updated in place.

## 2. Usage

```bash
python 0.mark_rank_transitions.py
```

Optional arguments include `--input`, `--ratio`, and `--min-total`.

# 1.compute_phase_versions.py

This script analyzes the distribution of key versions across the `before`, `during`, and `after` phases for the two migration scenarios. These phases are the paper's pre-deprecation period, source-definition transition period, and post-removal period, delimited by `Va-1` (the final pre-announcement release) and `Vd` (the source-definition removal version).

## 1. Overview

- Reads `fix_D.xlsx` and `fix_R.xlsx`;
- Processes only the `class_transition`, `function_transition`, and `method_transition` worksheets;
- Counts only rows whose column K, `Key_Versions`, is non-empty;
- Extracts the version sequence from the `order` field of the version-pair JSON;
- Divides the sequence into `before`, `during`, and `after` according to `Va-1` and `Vd`;
- Records the three phase counts and `key_version_count` for each case;
- Generates summaries organized by migration scenario and API granularity;
- classifies each parsed key version into `before`, `during`, or `after` and records the phase-level key-version counts as `key_before`, `key_during`, and `key_after`.

The script uses the version after `->` in a key-version transition. For `fix_D`, it selects the right-hand version of the transition pair; for `fix_R`, it selects the left-hand version. Invalid or unresolvable key-version entries are skipped.

### Function structure

- `split_version()`: parses version-pair strings, including version names containing hyphens;
- `_normalize_version()`: normalizes version strings by removing surrounding whitespace and a leading `v`;
- `_phase_for_index()`: maps a version position to the `before`, `during`, or `after` phase;
- `count_key_versions_by_phase()`: counts key versions in each phase;
- `process_sheet()`: processes one transition worksheet and produces case-level records;
- `process_experiment()`: loads one migration-scenario workbook and groups worksheet results by API granularity;
- `build_aggregate_summary()`: constructs the overall summary for each migration scenario.

## 2. Usage

```bash
python 1.compute_phase_versions.py
```

The script does not require command-line arguments. The input and output locations are determined by the path configuration in the code.

## 3. Input Parameters

The script reads the following data:

| Data | Location | Purpose |
|---|---|---|
| First column | Excel column 1 | Combined with the second column to form the case identifier |
| Second column | Excel column 2 | Combined with the first column to form the case identifier |
| `Va-1` | Excel column 5 | Determines the boundary of the `before` phase |
| `Vd` | Excel column 6 | Determines the boundary between the `during` and `after` phases |
| Version-pair JSON | Excel column 8 | Provides the version sequence |
| `Key_Versions` | Excel column K | Non-empty rows are included; used to calculate the number of key versions |

## 4. Output Structure

The output JSON is organized as follows:

```text
fix_D / fix_R
    └── class / function / method
        ├── cases
        │   └── case, before, during, after,
        │       key_version_count, key_before, key_during, key_after
        └── summary
            └── case_count, before, during, after,
                key_version_count, key_before, key_during, key_after

summary
    └── fix_D / fix_R
        ├── class / function / method
        └── overall
```

For each migration scenario, the top-level `summary` combines the three API granularities and provides both per-granularity and overall totals.

The output file is:

```text
output/phase_versions_summary.json
```

# 2.analyze_cases.py

This script compares candidate-API ranking changes between `Vi-1` and `Vi` for each case and attributes the dominant causes of the key versions.

## 1. Overview

The script:

- walks through cases containing a `result/` directory;
- locates the `Vi-1` and `Vi` version directories;
- reads the ranking JSON for the three algorithms;
- analyzes ranking changes for the target replacement API `R_FQN`;
- counts candidate-API disappearance, ranking changes, and similarity changes;
- obtains a cause classification for each algorithm;
- combines the non-special cause classifications into the case-level
  `final_cause`; `special` classifications are ignored during this step.

The main cause categories are:

```text
candidates
dep_rep
combined
special
undetermined
```

The `cause` field in `cause_classification.json` is an algorithm-level classification. `special` means that the algorithm's ranking did not change; it is not a cause and is excluded from case-level attribution because it provides no evidence for the key-version transition. Since a key version is retained only when at least one algorithm reaches the 10% rank-change threshold, valid cases retain at least one non-special result, from which `final_cause` is determined as `candidates`, `dep_rep`, or `combined`.

For this script's intermediate labels, `candidates` corresponds to the final `candidates_cause` directory (paper: **other-candidate-dominant**), `combined` corresponds to `common_cause` (paper: **mixed**), and `dep_rep` corresponds to `dep_rep` (paper: **pair-dominant**).

## 2. Usage

```bash
python 2.analyze_cases.py
```

## 3. Input Parameters

The script has no command-line arguments. Its main inputs are:

- `CASES_ROOT`: the case root directory;
- `ALGORITHMS`: the list of algorithms to analyze;
- `result/Vi-1*/` and `result/Vi*/` under each case;
- `mapBased.json`, `tokenBased.json`, and `treeBased.json` under each version directory.

## 4. Output Structure

The classification results are saved to:

```text
output/cause_classification.json
```

The JSON keys are:

```text
fix_D-<case-name>
fix_R-<case-name>
```

The value contains the cause classifications for each algorithm and the final cause:

```json
{
  "fix_D-<case-name>": {
    "mapBased": {
      "cause": "candidates",
      "special_reason": null
    },
    "tokenBased": {
      "cause": "dep_rep",
      "special_reason": null
    },
    "final_cause": "combined"
  }
}
```

# 3.analyze_rcandidates_threshold.py

This script analyzes whether the number of candidate APIs in the `fix_D` scenario changes by at least 10% from `Vi-1` to `Vi`.

## 1. Overview

For each case, the script:

1. Recursively counts the `.py` files in `Vi-1`;
2. Recursively counts the `.py` files in `Vi`;
3. Calculates the candidate-file count change rate;
4. Determines whether the absolute change rate reaches 10%;
5. Aggregates the results by cause category, consistency category, and API granularity.

## 2. Usage

```bash
python 3.analyze_rcandidates_threshold.py
```

## 3. Input Parameters

The script has no command-line arguments. It reads `cases_split/` in the script's directory and processes:

- `candidates_cause`, `common_cause`, and `dep_rep`;
- `fix_D`;
- `consistent` and `no_consistent`;
- `class`, `function`, and `method`.

A case may be an actual directory, a symbolic link, or a text file containing a relative-path reference.

## 4. Output Structure

The output file is:

```text
output/R_candidates_threshold_details.json
```

The results are organized by cause category, consistency, and granularity. For example:

```json
{
  "candidates_cause/fix_D/consistent": {
    "total": 43,
    "exceed": 40,
    "pct": 93.0,
    "details": [
      {
        "case": "...",
        "granularity": "class",
        "vi1_py": 100,
        "vi_py": 115,
        "change": 15,
        "change_rate": 0.15,
        "exceeds_10pct": true
      }
    ]
  }
}
```

# 4.analyze_rc_py_stats.py

This script provides a detailed analysis of changes in the candidate-API file set from `Vi-1` to `Vi` in the `fix_D` scenario.

## 1. Overview

For each case, the script compares the `.py` filenames and file contents in the two versions and counts:

- deleted candidate-API files;
- newly added candidate-API files;
- files shared by both versions;
- shared files whose contents are identical;
- shared files whose contents changed;
- the total number of changes and the corresponding change ratios.

## 2. Usage

```bash
python 4.analyze_rc_py_stats.py
```

## 3. Input Parameters

The script has no command-line arguments. It reads `cases_split/` in the script's directory and analyzes:

- `candidates_cause`, `common_cause`, and `dep_rep`;
- `fix_D`;
- `consistent` and `no_consistent`;
- `class`, `function`, and `method`.

Each valid case must resolve to an actual directory containing:

```text
<case>/
├── analysis.md
└── R_candidates/
    ├── Vi-1_*/
    └── Vi_*/
```

## 4. Output Structure

The script generates three JSON files:

```text
output/
├── candidates_cause_rc_py_stats.json
├── common_cause_rc_py_stats.json
└── dep_rep_rc_py_stats.json
```

Each file contains:

```text
meta
cases
summary
```

Here:

- `meta`: overall case count, skipped count, and the cause/consistency/granularity distribution;
- `cases`: detailed candidate-file change statistics for each case;
- `summary`: aggregate statistics overall, by consistency, and by granularity.
